# Geolocation: extend the sandbox permissioning framework to location

Geolocation is the next member of the per-artifact first-use permission family alongside downloads (av-ryby), clipboard (av-hll6), external links (av-r0dk), and camera/microphone (av-mv3k): same per-artifact first-use decision, same persistence and revocability, same capability-badge/popover surface.

Like camera/microphone, a browser geolocation grant is per origin while every artifact shares one render origin, so a visitor who allowed location for one artifact opened directly has allowed it for every artifact on that origin. Permissions-Policy is per document, so the render response must carry a per-artifact geolocation policy built from the same approval, exactly as av-mv3k does for camera/microphone.

## Design

Scope mirrors av-mv3k:

Schema/store: geolocation_approved boolean on artifacts (next unused goose migration version). Accepted by PATCH /api/artifacts/:id exactly like camera_approved/microphone_approved, including strict-bool 400 on non-bool. Add to store.ApprovalColumns so the API and store validation cannot drift. Never seeds from scans, never affects the CSP.

Render surface (internal/render/render.go): extend buildPermissionsPolicy with a geolocation feature -> geolocation=(self)|(), set in serveDoc beside the CSP. Names only camera, microphone, geolocation; every other feature keeps its browser default. A widget render passes false whatever the artifact holds (unattended tile, no gesture to attribute a prompt to).

Frame gate inside bridgeScript (framed-only, absent from the widget preamble by construction): replace navigator.geolocation getCurrentPosition/watchPosition, report the request, and settle by invoking the error callback with a PermissionDenied PositionError — never resolving a position, never hanging. clearWatch is a no-op pass-through. Where navigator.geolocation is absent entirely, synthesize the minimal object rather than leaving an artifact to die on property access. Constraints/options stay in the frame: the host acquires nothing, so sending them would be data with no reader.

Host (web/gallery/detail.js): __avGeolocation listener validated like every other bridge message (e.source === frame.contentWindow, d.artifactId === ID). Unapproved -> prompt naming the location request; Allow persists only geolocation_approved and opens the top-level render (the click activation covers the PATCH roundtrip), where the browser enforces the new policy. Already approved -> no second prompt; the frame raises the capability banner instead. Every path settles the frame callback, including a request displaced by a newer one.

UI: first-use modal on the detail page; geo-select on the edit page security panel, dirty-flagged like cam-select/mic-select; ph-map-pin row and glyph in the capability cluster and popover; the Fully contained copy extended to cover the new flag.

Docs: security.md section 4 (capability-gate family), architecture.md sections 3.1/3.2/6, technical_stack.md section 4, PRD section 6.3 + 4.4 schema.

Open measurement question for implementation: verify in a real browser whether the opaque-origin frame refusal for geolocation is structural (like getUserMedia SecurityError in av-mv3k) and confirm the allow= iframe delegation is a no-op before removing/omitting it. If coordinates prove safely bridgeable (positions are plain numbers, unlike MediaStreamTracks), record why the gate was still chosen so a future bridge ticket can revisit it deliberately.

## Acceptance Criteria

PATCH /api/artifacts/:id {geolocation_approved: true|false} round-trips; a non-bool is a 400; approving location never approves camera/microphone and vice versa. An unapproved artifact render document carries geolocation=(); approving yields geolocation=(self), alongside the existing camera/microphone values. A share carries the owner approval; a widget render carries geolocation=() even when its artifact holds true. The detail-page iframe sandbox is unchanged (allow-scripts allow-forms) and carries no allow= delegation, whatever the approval state. The widget preamble contains no __avGeolocation (extends the existing strict-subset assertion); the artifact preamble does, inside the framed guard. The frame geolocation always settles: denial, displacement, and the already-approved case all invoke the error callback rather than hang. Browser-verified: unapproved preview prompts naming location; Allow persists the flag and opens the top-level render where the position actually resolves; second request shows the capability banner with no re-prompt.
