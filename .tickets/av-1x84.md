# Live state sync: the other person's change should appear without a reload

State is last-write-wins with no push, so two people on a shared artifact
clobber each other and neither sees the other's change until reload. A grocery
list tolerates that. A chess board does not: you move, and your opponent sits
looking at the old board.

Raised while designing av-g234 (writable shares). Shared state is Exhibit's
deliberate design — a share publishes the artifact's state, one board, not one
per person — so "the other person's move appears" is what that promise implies
and does not yet deliver.

Owner is brainstorming; a shim over websockets was the first idea. This ticket
exists to keep the constraints the codebase already imposes, so the design does
not start from a blank page.

## Design

Not a design, just the walls that are already up.

**The socket cannot live in the artifact frame.** connect-src governs WebSocket
as well as fetch, and the artifact's policy is the per-artifact allowlist plus
blob:/data: — never the app origin. Putting the app origin in there to carry a
socket would hand the artifact a direct line to the API, which is the exact
thing the postMessage bridge exists to avoid. So the connection belongs to the
HOST frame, same as the state write-through already does. The bridge becomes
bidirectional rather than gaining a new participant.

**The delivery mechanism into the artifact already exists in the DOM.** The
shim would take an inbound message from the host, update its cache, and
dispatch a synthetic `storage` event. That is precisely what browsers fire when
another context writes localStorage, so artifacts already written for multi-tab
sync get multi-PERSON sync with no new API and no cooperation from the author
— which is spec 5.3's whole promise ("no skill, no special artifact format").
Artifacts that ignore the event are no worse off than today.

**SSE may be enough, and already exists here.** Writes already go over HTTP PUT
through the host, so the missing half is only server->client. internal/agent
streams SSE, and av-rgp1 solved auth for the one route a browser cannot send
headers on (a single-use, short-lived, session-bound ticket in the query
string) — a pattern this could reuse rather than invent. A websocket buys
bidirectionality that may not be needed yet, and adds a protocol to the
deployment contract that operators' proxies have to be told about. Worth
deciding deliberately rather than by reflex.

**Key granularity decides how much LWW actually hurts, and the artifact
chooses it, not us.** An artifact storing one JSON blob under `state` loses a
whole list to a conflicting write. One storing `item:1`, `item:2` loses a
single item. Push narrows the window a lot because clients converge in
milliseconds instead of on reload, so per-key LWW may be adequate for real use
without any merge machinery. Worth measuring against a real artifact before
reaching for CRDTs.

**Presence is the other half of feeling tangible.** Knowing someone else is
looking at the board is most of what makes shared state feel shared, and it is
cheap once a connection exists. Probably a follow-on rather than part of this.

## Acceptance Criteria

1. A change one viewer makes appears for another viewer of the same artifact
   without a reload.
2. The artifact needs no cooperation: an artifact written against ordinary
   localStorage picks the change up, and one that ignores storage events is no
   worse off than today.
3. The connection is the host frame's. The artifact frame gains no new network
   reach, and connect-src still never carries the app origin.
4. Whatever authenticates the stream does not put a credential anywhere the
   artifact can read it.
5. An instance with no shared artifacts pays nothing for this.
