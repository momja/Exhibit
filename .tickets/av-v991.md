# Per-artifact public state policy: none / read-only / shared

av-wmp6 made anonymous public renders inline no state. That was a deliberate conservative default (reversible; publishing data you meant to keep private is not), not a product decision — and it is wrong for two real cases: publishing a leaderboard or dataset read-only, and a two-player artifact where both people act on one shared state (a remote chess game).

Make it a per-artifact policy with three values:

  none    — artifact boots empty for anonymous viewers (today's behaviour, stays the default)
  read    — anonymous viewers see the OWNER's state, read-only
  shared  — anonymous viewers read and write ONE common state

The three are not equal in cost. 'none' and 'read' are a column and a token claim. 'shared' reopens the anonymous write path and needs a principal that is deliberately not per-viewer. They should not ship together.


## Notes

**2026-08-06T16:54:18Z**

DESIGN

## Levels none/read — small, ship first

The seams exist. `internal/render` already decides whether to call `GetState` and with which principal, and `rendertoken` already carries an `Anonymous` claim (av-wmp6) that *subtracts* authority. Add:

- A column on `artifacts` (`public_state`, defaulting to 'none' so every existing artifact keeps today's behaviour).
- A third state on the token claim rather than a second boolean — 'anonymous' and 'may read owner state' are not independent, and two booleans admit a meaningless fourth combination.
- The claim must stay **inside the MAC**, for the reason av-wmp6 established: a claim that subtracts authority is one the viewer would otherwise simply delete. Widening it must be equally unforgeable.

'read' publishes the owner's state to anyone with the link, so the UI has to say so plainly at the moment of choosing — this is the setting most likely to be picked without reading.

## Level shared — gated, do not fold into the above

Two things the epic deliberately built have to be reopened, each on purpose rather than by loosening:

1. **A shared principal.** av-q0ub keyed state by `(artifact_id, user_id, key)` precisely so two viewers cannot see each other's rows. A shared board needs one designated principal both writers use. That is a second mode beside per-viewer isolation, not a relaxation of it — the isolation must remain the default and the shared principal must be impossible to reach unless the artifact is explicitly set to 'shared'.
2. **The anonymous write path.** av-wmp6 closed it: `ANONYMOUS` short-circuits `persistState` in the render preamble, so the frame never posts a write. Reopening it for one artifact needs a narrowly-scoped write credential; `rendertoken.Signer` already mints exactly that shape and should be the third caller rather than a new mechanism.

This is also the first path on which an **unauthenticated stranger writes to the operator's database**. av-wrbu owns the size-ceiling policy and av-q0ub already added state to its scope; per-artifact and per-principal ceilings stop being theoretical here. Rate limiting is a real question too, and neither exists yet.

## The limitation that will disappoint before any of the above does

There is no live channel. State is inlined **at render time** and writes travel one-way (shim → host frame → `PUT /state`). So a second player sees nothing until they reload, and the conflict policy is last-write-wins, which silently drops one of two simultaneous writes.

Chess is turn-based enough to survive LWW, but 'reload to find out whether they moved' is not the experience the feature implies. Making it live means polling or SSE on the render surface — a separate piece of work that 'shared' is close to useless without, and which should be scoped before anyone promises collaborative artifacts.

## Acceptance criteria (levels none/read only)

1. Default is 'none'; every existing artifact keeps av-wmp6's behaviour with no migration action.
2. 'read' inlines the owner's state for an anonymous public render; 'none' inlines nothing; an authenticated render of the same artifact is unaffected in both cases.
3. The policy rides inside the MAC and a token cannot be edited to widen it.
4. Shares (`/s/:shareId`) are unchanged — the share row is already a deliberate per-artifact decision to publish as the owner sees it.
5. 'shared' is not implemented here; the column accepts the value only once its own ticket lands, or the enum omits it entirely until then.

**2026-08-06T18:42:41Z**

CORRECTION AND SHARPENING (2026-08-06) — the 'shared' level, reconsidered

Two things the design note above gets wrong or misses.

## 1. The flag belongs on the SHARE ROW, not the artifact

`shares(id, artifact_id, public, expires_at)` already is the unit of 'I am giving this to someone'. Add `shared_state` there instead of to `artifacts`:

- One person can hold a read-write link and another a read-only link to the same artifact. An artifact-level flag cannot express that at all.
- **Revoking the share revokes the write access in the same motion** — no second lifecycle to remember, and no orphaned grant pointing at an artifact whose link you already withdrew.
- It matches how the security model already reasons: architecture.md §7 says the share row *is* the authorization. Making it also carry what that authorization permits is consistent rather than novel.

## 2. There is no write path from a share at all — this is structural, not policy

`serveShare` on the app origin 302s to `RENDER_ORIGIN/s/:shareID`, so a share renders **top-level**. The document therefore has no parent frame, and `persistState` bails on `window.parent === window` — correctly, since a sandboxed opaque-origin document cannot reach the API itself.

So a share link can already *read* inlined state but has nowhere to send a write. Level 'shared' is not 'relax a check'; it is 'build the missing half'. Concretely:

1. **Stop redirecting the share.** Serve `/s/:id` as an app-origin page embedding the render iframe, the way the gallery and detail pages already do. That restores the host-frame bridge and keeps the render surface **read-only**, which is what makes it safe to expose with no auth (architecture.md §3.2). Letting the render origin accept writes would surrender that property and should not be the chosen path.
2. **A second accepted credential on `PUT /api/artifacts/:id/state`** — a render token with a shared-write claim, resolving the principal to the share's shared principal rather than the viewer's. `rendertoken.Signer` already mints exactly this shape; make it a third caller, not a new mechanism. Note this is the first credential other than a session or the service token to reach a mutating route, so it wants the same care av-ke2m's CSRF section applies to the others.
3. **Shim guard.** `ANONYMOUS` currently short-circuits `persistState` outright; it needs to distinguish 'no principal' from 'a shared principal I am permitted to write to'.
4. **Quotas and rate limiting.** First path on which someone with no account writes to the operator's database. av-wrbu owns the ceilings; this is what makes them non-theoretical.

## Which shared principal

Simplest is the artifact's own `owner_id` — 'shared state means everyone writes into the owner's rows'. It needs no new principal space and makes the owner's own view of the artifact identical to the shared one, which is what you want for a game you are playing. A synthetic per-share principal is more isolated but means the owner sees a different board than the person they invited, which is exactly wrong for this use case.

## Still true from the earlier note

Per-viewer isolation (av-q0ub) must remain the default and the shared principal must be unreachable unless the share explicitly says otherwise.

**2026-08-06T18:48:30Z**

AFFORDANCE: how the user tells shared from private (2026-08-06)

Starting fact: **today they cannot.** A gallery card shows nothing about sharing, and `ListArtifacts` carries no share data at all — no join, no count — so the gallery could not display it even if the template wanted to. The only way to learn an artifact is shared is to open it and look at its share controls. That is survivable while a share publishes a *file*; it stops being survivable when a share carries live, writable state.

## Encode the ladder, not a boolean

The states are ordered by how much authority has left the owner's hands:

    private             no share row
    link, no state      they can run it; they see nothing of the owner's
    link, publishes     they see the owner's data
    link, shared state  they can change the owner's data

Because it is a ladder, this is **one badge with escalating treatment**, not four independent flags. The badge names the strongest thing true.

**Private gets no marker.** The absence is the signal — a library of forty cards must not render forty badges, and marking the default trains people to ignore the marker. av-isb3 already established the capability-row badge + popover pattern; follow it rather than inventing a second vocabulary.

Requires `ListArtifacts` to learn about shares (a denormalized count/max-level on `artifacts`, kept current the way `tags_text` already is, is likely cheaper than a join on every gallery render — see av-b6o9 for the existing precedent).

## The visitor's half matters more

The owner opted in. The person handed a link opted into nothing, and on a shared-state artifact their actions are visible to a stranger. The share page must say so plainly — not a badge, a sentence, on the page. av-v991's move away from a 302 to a real app-origin share page is what makes this possible; do not let that page ship as a bare iframe.

## One accidental signal, worth stating deliberately

With shared state the card's widget tile renders the **shared** state, so the owner's gallery shows the other party's writes. That is genuinely useful — it is the chess board updating on the shelf — but it means a tile becomes a window onto someone else's input. State it as a property; do not let it be discovered.

## The failure mode to design against: the forgotten share

Something shared eight months ago, still carrying live state. Two consequences:

1. The badge must be **ambient** — visible without hover or click — or it does not help the person who has forgotten.
2. The user must be able to **enumerate** what is currently shared. A filter or a 'Shared' view; you cannot audit what you cannot list.
3. `shares` already has `expires_at`, currently unused for this. **Defaulting state-carrying shares to an expiry is probably the highest-value safety default available here.** A read-only file share can live forever harmlessly; a writable one should not. Consider making an unbounded lifetime the deliberate choice rather than the default, for the 'shared' level only.

TOKEN ENCODING — do this before adding the shared-write claim (2026-08-06)

Question raised: should render tokens be JWTs? **No** — but the positional encoding must change, and this ticket is what forces it.

## Why not JWT

1. **It would give up a structural guarantee.** The artifact id is not a *field*; it is mixed into the MAC. A token minted for artifact A does not fail an equality check on B's route — it fails to verify at all, so there is no comparison a future verifier could forget to write. As a JWT this becomes `aud` plus the discipline of checking it at every call site. Structural beats disciplined.
2. **Size, concretely.** The token lives in a URL: ~55 chars today, 150–200 as a JWT once a header and payload are base64'd. URLs reach browser history and server logs regardless of the no-referrer header av-nr0p added.
3. **JWT's flexibility is its CVE surface** (`alg: none`, HS/RS key confusion, `kid` injection) and exists to serve many issuers, algorithms and key sources. This has one of each.

Note the usual counter-argument no longer applies: `go-jose/v4` and `golang-jwt/jwt/v4` are already in the module graph as indirect dependencies of go-oidc. Rejecting JWT here is a design call, not dependency avoidance.

## What to change instead: named claims, not positional

The wire format has gone `owner.exp.tag` → `owner.exp.a.tag`, and this ticket adds at least a shared-write claim and probably a share id. Optional positional fields become fragile fast — that is the real problem.

    v1.<base64url("o=1&e=1785948001&a=1&s=shr_abc")>.<hmac>

- MAC still covers version ‖ artifactID ‖ payload. Keep both properties above.
- Adding a claim no longer disturbs the ones beside it.
- No algorithm field, so nothing to negotiate or confuse.
- **Reject unknown fields.** JWT ignores unrecognized claims by spec, which means a token stripped of a claim the verifier did not know about passes silently. For claims that *subtract* authority (anonymous; read-only-shared) that is the wrong default — fail closed.
- Keep the existing 'optional and last means byte-identical to the previous format' migration trick if a staged deploy needs it, or accept a short TTL window and cut over cleanly (TTL is 10 minutes; in-flight tokens age out fast).

Contained to `internal/rendertoken` plus its callers' claim construction. Doing it before the shared-write claim is cheaper than after.

**2026-08-09T17:47:05Z**

SCHEMA DEPENDENCY BROKEN (2026-08-09): shares.expires_at no longer exists

The affordance note above recommends defaulting state-carrying shares to an expiry, calling `expires_at` 'already there and unused' — the cheapest safety default available. av-8ipt has since **dropped the column** (migration 015), on the grounds that nothing ever set it and removal was free while every value was NULL.

That does not invalidate the recommendation, but it changes its price. An expiry on a shared-state link is now a column to add rather than a dial to turn, and it should be added deliberately as part of whichever level ('read' or 'shared') actually wants it — designed against that requirement rather than inherited from a guess. That is precisely the reasoning av-8ipt used to remove it, so re-adding it for a real use case is consistent rather than a reversal.

Nothing else in this ticket changes. If the 'shared' level is built, revisit whether a deadline belongs on the share row beside `shared_state` — the two would be the same row and the same lifecycle.

**2026-09-05T16:53:03Z**

DECISION (2026-09-05): anonymous shares write state, and "whose rows" becomes a
per-share setting

Two calls land together, from the same conversation as av-0k5q's directed-share
decision.

## 1. The anonymous share is a chess board in the park

One board. Anyone who walks up moves a piece. Nobody signs in, nobody is
addressed, and nobody owns their moves. The link is the whole membership rule.

An anonymous visitor has no principal of their own, so there is nothing to
isolate them into, and isolating them would be wrong anyway. Two people on one
link are two hands on one board.

**The board is the owner's rows.** This settles the fork the 2026-08-06 18:42
note left open, in favour of its simplest option. The owner walks up and sees
the position the stranger left, which is what a shared game means. A synthetic
per-share principal hands the owner a different board from the person they gave
the link to, which is exactly wrong for this use case.

**The cost is stated, not mitigated.** Anyone holding the link writes into the
owner's state rows for that artifact. There is no identity at the door, so there
is no access control to offer, and the whole safety story is ceilings (av-wrbu),
rate limiting, and deleting the row. An anonymous writable share is not a place
for critical data, and the share UI must say that in those words. Do not dress
it as a permission model.

## 2. A named recipient changes the question

av-0k5q chose directed shares, so a share can now name who is opening it. That
recipient has a principal, which means av-q0ub's per-viewer keying works for
them with no new mechanism. Two state modes, on the share row beside the flag
the 18:42 note already puts there:

    own      the recipient writes their own rows (needs a named recipient)
    shared   everyone on this link writes the owner's rows (the park board)

An anonymous link can only be 'shared' or read-only, since there is no viewer to
give rows to. A directed share can be either, and 'own' is the safer default for
it: a person invited to use your tool should get their own saved config unless
you meant to play a game with them.

## Unchanged

The write path still does not exist. serveShare 302s to the render origin, the
document is top-level, and persistState returns early on
window.parent === window, so a share's writes vanish today. Building this still
means either serving /s/:id as an app-origin page that embeds the frame (keeping
the render surface read-only) or accepting a share-scoped write credential on
PUT /state. There is still no live channel, so two people on one board reload to
see each other's moves, and simultaneous writes are last-write-wins.

TOKEN ENCODING, CONCRETE (2026-09-05) — supersedes the 2026-08-06 21:48 sketch

That note is right that positional encoding has to go and right to reject JWT.
Two of its specifics are wrong, and the claim set matters more than either.

## The claim set, which is the actual change

Claims.OwnerID does two jobs today: it authorizes the read (checked against the
artifact's owner) and it selects whose state gets inlined. Same person on every
route that exists. On a directed share they are different people, so this is
av-q0ub's two-principal split arriving at the token.

    o   owner whose artifact this is; authorizes the read      required
    e   expiry, unix seconds                                   required
    p   principal: whose state rows to inline                  absent = same as o
    a   anonymous: no principal at all                         absent = not anonymous
    s   the share row this render happens under                absent = not a share

p defaulting to o is what keeps every token minted today byte-identical and
costs the common case nothing.

Keep 'a' as its own key rather than collapsing it to p=0. av-wmp6's argument is
that anonymous SUBTRACTS authority and must be unforgeable, and p=0 invites a
"0 is falsy, treat as unset" bug that silently promotes a nobody to the owner.
A token carrying both a and p is rejected at parse rather than resolved.

## Wire

    o=1.e=1785948001.<tag>                  today's token plus one byte
    o=1.e=1785948001.p=7.<tag>              directed share, viewer 7's rows
    o=1.e=1785948001.a=1.<tag>              anonymous
    o=1.e=1785948001.p=1.s=shr_abc.<tag>    share, everyone on the owner's board

1. **No version in the wire.** The sketch proposed v1.<payload>.<tag>. Version
   stays inside the MAC where it already is, so a v2 token still fails a v1
   verify as garbage. What a wire version buys (two verifiers during a rollout)
   the 10-minute TTL already buys: cut over and let in-flight tokens age out.
2. **No base64 wrapping.** The sketch proposed encoding the payload. It costs
   33% on a value that lives in a URL and buys nothing. The fields are already
   URL-safe and LastIndexByte('.') still cuts the tag unambiguously, since
   base64url contains no dot. Readable claims are worth something in a log.
3. **Reject duplicate keys.** The load-bearing rule. o=1.o=2 must not parse
   whatever a last-wins reader would do with it.
4. **Reject unknown keys.** Already the behaviour for the one optional field,
   now general.
5. **No value contains '.' or '='.** Enforced at mint and at parse, not assumed.

Sorted key order is one more line and makes the encoding canonical, so one
claim set has exactly one byte string. Belt and braces next to rule 3.

Unchanged and worth keeping: the tag is the last field, the artifact id is mixed
into the MAC rather than carried, so adding a claim changes what is parsed and
never what is authenticated.

## The write credential does not ride in the URL

No w=1 claim on the render token. That would put a write credential in
location.href, which reaches browser history and the operator's proxy access
log — the exact reasoning av-rgp1 used to keep the SSE credential out of a URL,
and a write credential is worse than a read one.

Instead the URL token stays read-only and the render preamble INLINES a separate
short-lived write credential into the document, beside the state it already
inlines. Same Signer, same key, different delivery. The artifact can read it
either way, which is fine because the state is the artifact's own; the point is
that it never reaches a log and it dies with the document.

Do this encoding change before any new claim. It is contained to
internal/rendertoken plus the mint call sites, and it is the same work later
plus a format migration.

LIVE CHANNEL (2026-09-05) — shrink the window, do not solve merge

The 2026-08-06 note calls the missing live channel the thing 'shared' is close
to useless without, and leaves it unscoped. Scoping it now, because a directed
share in 'shared' mode is two accounts on one board and is in v1 (av-7k7b), even
though the anonymous board is not.

Two problems get conflated and only one is solvable here.

**Liveness.** B does not see A's write until reload. Fixable, cheaply.

**Merge.** Two writes to one key, one wins. Not fixable at the shim layer. A
grocery list kept as one JSON blob under one key loses an item whenever two
people add at once, however fast the channel. CRDTs are the real answer and are
far outside this product.

The observation that makes the first one worth doing: merge's window is
proportional to liveness latency. At reload-to-find-out latency every concurrent
session loses writes. At 200ms, B's next add is a read-modify-write over fresh
data and nothing is lost. Fixing liveness dissolves merge for the two-person,
coarse-turn case, which is the only case this feature should promise.

## Three pieces, cheapest first

**1. Fire real StorageEvents.** When the shim learns the server's copy changed,
update the cache and dispatch a 'storage' event on window. That is the
platform's own mechanism for "another tab wrote this", so an artifact written to
the standard contract gets multi-player with no new API and no cooperation from
its author. Do this whatever the transport is. Artifacts that ignore 'storage'
still need a reload, which is what they would have needed anyway.

**2. SSE from the render origin.** GET /a/:id/state/events, pushed on write,
fanned out from an in-memory hub — the shape internal/agent already runs for
Pi's stream, and cheap because the service is one process. It needs connect-src
to carry the artifact's own event path, which is precedented: av-20fk adds the
artifact's own asset path as a SYSTEM source, added by the render surface and
never by approval. The same argument holds (the artifact reaching its own bytes
on its own origin grants nothing new), so this touches neither the allowlist nor
the approval UI.

**3. Resync on focus.** Alongside SSE, not instead of it. A tab backgrounded for
an hour should refetch on visibilitychange rather than trust a connection that
died quietly. This is the "opened the list again at the store" case, which is
the actual usage.

## Later, if at all

Versioned writes: PUT /state carries the version the shim last read, the server
rejects a stale one and returns current, the shim fires a storage event with it.
That turns a silent overwrite into a visible one. Only worth building if real
conflicts show up, and with the three above a two-person list will not generate
any.

## What the UI must not promise

The honest ceiling is small groups taking coarse turns. Do not let the share UI
imply collaborative editing.
