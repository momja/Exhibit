# Top-level render silently discards state writes

Opened top-level at RENDER_ORIGIN/a/:id — the "Open in new tab" destination —
or through a share at /s/:shareID, an artifact's localStorage writes update the
in-memory cache and are then discarded. Reads are correct; nothing persists.

Verified: set a key top-level, reload, read it back as null.

The mechanism is one guard in the render preamble's persistState:

    if (window.parent === window) return; // top-level: no host to persist through

That is accurate — the write-through bridges through the embedding app-origin
frame, and top-level there is no frame. It is also invisible. The artifact's
setItem returns normally, its own in-memory reads keep working for the life of
the page, and the value is gone on reload.

Where this matters most is the case we actively steer people into. av-yvtb
(module workers) and av-mv3k (camera/microphone) both tell the user to open the
artifact directly, because the opaque-origin sandbox cannot provide those. A
signed-in owner who follows that advice with a stateful artifact — a todo list,
a tracker, saved settings — loses whatever they enter, with no indication.

Note the asymmetry with the branch immediately above it. ANONYMOUS returns
early too, and carries an argument for why that is right: "Not persisting is
honest; persisting into a void is not." The top-level branch does the same
thing with no such reasoning recorded and no signal to the user.

## Design

## Persisting top-level is not a small fix, and for shares it is a hole

The obvious repair — give the top-level document a way to write through — is
closed twice over, and both closures are load-bearing:

- RENDER_ORIGIN holds no session and sets no cookie (security.md §1.3,
  asserted by a test over every route). A top-level render is a real-origin
  document with the artifact's own script in it, so any credential readable
  there is readable by the artifact. It therefore has nothing to authenticate
  a write with.
- connect-src is `blob: data:` plus the artifact's allowlist and never the app
  origin, so the document could not reach the API even holding one.

**And a share must not gain a write path at all.** ServeShare renders as
`rendertoken.Claims{OwnerID: a.OwnerID}` — deliberately, so a link recipient
sees the artifact as its owner sees it. If top-level writes persisted, an
unauthenticated share recipient would be writing into the *owner's*
artifact_state rows. Consequences, in order of severity:

1. Arbitrary state injection as the owner. The owner opens their artifact and
   the shim inlines whatever a stranger wrote. State is inlined as
   json.Marshal output inside a <script>, so there is no script breakout — but
   an artifact that renders a stored value into innerHTML would execute
   attacker markup inside the owner's frame. Bounded by the sandbox and the
   artifact's own CSP; not bounded to nothing.
2. There is no cap on state value size or row count anywhere in state.go, so
   an anonymous writer could balloon the owner's database.
3. av-q0ub keys state by (artifact_id, user_id) and a share recipient has no
   user_id. There is no correct answer to "whose rows" for them short of
   inventing an identity they do not have.

So any design here has to treat the two cases separately, and the share case
almost certainly stays read-only whatever happens to the owner case.

## Shapes worth weighing

- **Say so and stop there.** The cheapest honest answer: the top-level render
  states that state is not saved in this view, and links back to the artifact's
  page. No new write path, no new surface. Interacts with av-tan0, which asks
  the same "what may we draw inside a document we do not control" question for
  blocked origins — the two should be decided together.
- **Make the owner's case work.** Would need a credential the render origin is
  specifically designed not to hold. A signed, artifact-scoped, short-lived
  write token in the style of av-c5aq's render token is conceivable, but it
  puts a writable credential into a document the artifact can read, which is
  the exact thing §1.3 exists to prevent. Hard to justify.
- **Do not send people top-level for stateful artifacts.** Narrow the advice
  rather than the mechanism: av-yvtb's and av-mv3k's "open it directly" copy
  could warn when the artifact has stored state.

## Also worth recording while here

localStorage is shimmed unconditionally, including top-level
(`Object.defineProperty(window, 'localStorage', ...)` outside the framed
guard). Framed that is a necessity — the opaque origin makes the native getter
throw on property access. Top-level it is a choice, and it has a second benefit
the comment does not mention: it is why localStorage is the one Web Storage
surface that does NOT leak between artifacts on a shared render origin.
sessionStorage and indexedDB are not replaced top-level and do fall through to
the origin's real, shared stores.

## Acceptance Criteria

1. A user who opens a stateful artifact top-level is not left believing their
   changes were saved. Either they persist, or the view says they will not.
2. No unauthenticated share recipient can write into the owner's
   artifact_state, whatever else changes. A share stays read-only for state.
3. If any top-level write path is introduced, the credential it uses is not
   readable by the artifact, and security.md §1.3's guarantee is restated in
   terms of whatever replaces it.
4. The decision is written down in security.md either way, so the guard in
   persistState carries the same kind of reasoning its ANONYMOUS neighbour
   already does.
